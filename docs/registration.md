# Регистрация

`RegisterController` получает `RegistrationService`, `Executor` и `Navigator` через
конструктор. Привязки находятся в `AppServiceProvider`. Контроллер считывает четыре
поля, очищает поля паролей и передаёт `RegistrationRequest` фоновой задаче.
Во время запроса отправка и переход на другую страницу заблокированы.

`DefaultRegistrationService` проверяет форму через `RegistrationValidator`,
проверяет уникальность через `RegistrationRepository`, вычисляет хеш через общий
`PasswordHasher` и сохраняет пользователя. Хеширование выполняется до INSERT,
без удержания соединения или транзакции. Сервис не зависит от JavaFX.

## Правила

Логин и пароль проверяются общим классом `app.validation.CredentialRules`, который
используется также формой входа. Почта и повтор пароля проверяются только при регистрации.

| Поле | Проверка |
| --- | --- |
| Логин | 3–128 символов: латинские буквы, цифры, `.`, `_`, `-`; внешние пробелы удаляются |
| Почта | Не более 254 символов, локальная часть до 64; обычный ASCII-адрес с доменом из нескольких меток; поддерживаются `+tag` и Punycode |
| Пароль | 15–128 кодовых точек Unicode; нельзя состоять только из пробелов |
| Повтор пароля | Обязателен и совпадает с паролем точно, включая пробелы и регистр |

Пароль не обрезается и не нормализуется; допускаются фразы и Unicode. Обязательных
цифр, заглавных букв и специальных символов нет. Минимум 15 выбран для входа без MFA
с учётом [рекомендаций OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#implement-proper-password-strength-controls).
Проверки по базе скомпрометированных паролей пока нет.

Почта приводится к нижнему регистру — это политика идентификаторов этого приложения,
согласованная с существующим `COLLATE NOCASE`. Кавычки в локальной части, IP-литералы
и Unicode-адреса напрямую не принимаются; это ограничение формы, а не универсальная
проверка всех допустимых почтовых адресов. Проверяется синтаксис, без отправки письма
и подтверждения владения адресом.

## Уникальность и результат

Предварительная проверка возвращает ошибки сразу для обоих занятых полей и позволяет
не вычислять хеш для заведомого дубликата. Окончательную уникальность обеспечивают
ограничения `users.login` и `users.email` в БД.

`SqliteRegistrationRepository` распознаёт именно `SQLITE_CONSTRAINT_UNIQUE`, повторно
определяет занятые поля и выбрасывает `DuplicateAccountException`. Сервис превращает
его в `RegistrationResult.InvalidInput`. Прочие ошибки БД остаются исключениями.
Для другой СУБД нужна другая реализация `RegistrationRepository` с переводом её
ошибок уникальности; контроллер и сервис менять не нужно.

`RegistrationResult.Success` содержит ID созданной записи. В БД записываются логин,
почта и хеш; даты и версия выставляются схемой. Повтор пароля не сохраняется.
Все ошибки формы показываются вместе, ошибочные поля выделяются рамкой.
Соответствие полей ошибкам задаётся только в FXML через стандартные `properties`:

```xml
<PasswordField fx:id="registerPasswordConfirmField">
    <properties validationField="passwordConfirmation" validationDependsOn="password" />
</PasswordField>
<Label fx:id="feedbackLabel">
    <properties validationFeedback="true" />
</Label>
```

`validationField` — имя поля в результате проверки, `validationDependsOn` — поле,
изменение которого также снимает эту ошибку. Метка `validationFeedback` указывает
место для сообщений. Это [стандартные свойства Map в FXML](https://openjfx.io/javadoc/26/javafx.fxml/javafx/fxml/doc-files/introduction_to_fxml.html#read_only_map_properties),
без пользовательских визуальных компонентов и библиотек для загрузки шаблона.

Общий для форм `app.ui.FormFeedback` читает декларации из готового дерева FXML и
снимает сообщение и рамку изменённого поля,
сохраняя ошибки остальных полей. Изменение пароля также снимает ошибку его повтора.
Ошибки снова появляются только после отправки формы; ввод сам по себе не запускает
валидацию или запросы в БД. Общие сообщения об ошибках исчезают при изменении любого поля.
Контроллер передаёт результат через `FormFeedback.showValidation(form, errors)`.
В нём нет списка привязок ошибок или зависимостей полей. Сам контроллер обрабатывает
отправку, собирает запрос к сервису и управляет ходом операции. Модель пользователя
не зависит от элементов интерфейса. Отдельных классов форм регистрации и входа нет.
После успеха повторная отправка отключена, а кнопка LOGIN в шапке открывает вход.
Регистрация и создание сессии — два отдельных действия: успешное сохранение аккаунта
не зависит от доступности DPAPI. Уже созданным аккаунтом можно войти через существующий
сервис аутентификации.

## Проверки

- `./scripts/test-registration.ps1`: границы полей, нормализация, совместимость хеша
  с входом, уникальность, гонки двух регистраций, ошибки БД, отмена и очистка паролей.
- `./scripts/test-ui.ps1`: настоящий FXML, DI, передача четырёх полей, фоновый вызов,
  сообщения, подсветка, блокировка отправки, переход к входу и переполнение исполнителя.
  Снимки формы записываются в `.deps/registration-validation.png` и
  `.deps/registration-success.png`.

Проверки используют временную SQLite-базу. Рабочие пользователи не создаются.
Новая миграция не требуется: используются существующие поля и UNIQUE-ограничения.
