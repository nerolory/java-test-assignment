# Ядро приложения

## Провайдеры и зависимости

`core.contracts.ServiceProvider` задаёт метод регистрации зависимостей.
`core.container.ServiceContainer` вызывает провайдеры, хранит привязки и создаёт
объекты. Классы не зависят от JavaFX, контроллеров или сервисов приложения.

Контейнер настраивается в одном потоке при запуске, до его использования другими
потоками. `register(provider)` вызывает провайдер; `bind(type, factory)` создаёт
объект при каждом обращении; `instance(type, object)` возвращает один общий объект.
`resolve(type)` получает объект по контракту. Повторная привязка, отсутствующая
регистрация, циклическая зависимость и null из фабрики вызывают явные ошибки.
Жизненным циклом общих объектов, включая close(), управляет приложение.

Конкретные привязки находятся в `app.providers.AppServiceProvider`. Контроллеры
получают зависимости через конструкторы и не обращаются к контейнеру.
В точке запуска JavaFX использует `loader.setControllerFactory(services::resolve)`.
Это также работает для контроллеров вложенных fx:include; сам FXML зависимостей
не содержит. Проверки контейнера и загрузки страниц: `scripts/test-ui.ps1`.

## Хеширование и хранение секретов

Общие контракты `PasswordHasher` и `SecretStore` находятся в `core.contracts`.
Их реализации в `core.security` обеспечивают PBKDF2 и защищённый DPAPI-файл.
Правила входа, срок сессии и запросы пользователей остаются в `app`; см.
[описание входа](authentication.md).

## Работа с БД

Ядро не зависит от JavaFX и классов приложения. Сейчас реализована и проверена
SQLite. Подключение другой СУБД требует её адаптера, диалекта и интеграционных
проверок; наличие интерфейса само по себе не гарантирует переносимость.

## Ответственности

| Компонент | Назначение |
| --- | --- |
| DatabaseConfig | Настройки SQLite и чтение properties |
| DatabaseOptions | Ограничения одного экземпляра приложения |
| DatabaseConfigurator | Сборка БД из адаптера либо внешнего DataSource |
| DatabaseConnector | Соединения, ограниченная очередь, commit/rollback |
| SqlDialect / SqliteDialect | Кавычки, пагинация, контроль выполнения SQL |
| Database | Запросы, транзакционная сессия, отмена и счётчики |
| QueryBuilder | Неизменяемые условия, выборки, проекции и CRUD |
| Model / ModelQuery | Сохранение с проверкой версии и выборка моделей |
| TransactionContext | Внутренний: активная транзакция текущего потока (без глобальной БД) |
| DatabaseTasks | Ограниченный исполнитель фоновых сценариев |
| app.models.User | Поля пользователя и преобразование данных |

## Модели и конфликты

```java
User user = User.on(database).where("email", email).firstOrFail();
user.setEmail(newEmail);
user.save();
```

Объект БД всегда передаётся явно: `User.on(database)`, `User.find(database, id)`,
`new User(database)`. Глобальной БД и статических запросов без неё нет, поэтому
зависимость видна в коде, а тесты с разными базами не мешают друг другу.
`first()` возвращает Optional, `firstOrFail()` — модель или ModelNotFoundException.
`where()` только строит запрос. Обращение к БД происходит при чтении результата.

Таблица модели содержит генерируемый целочисленный `id` и `version INTEGER NOT NULL`.
`save()` выполняет INSERT либо UPDATE с условием `id = ? AND version = ?`, затем
читает полученную строку в той же транзакции и на том же соединении. Версия
обновлённой записи увеличивается на единицу. Устаревшие save/delete вызывают
OptimisticLockException; удалённая строка также считается конфликтом.

При конфликте приложение перечитывает данные и принимает решение о слиянии.
Автоматически повторять сохранение устаревших полей нельзя. `refresh()` явно
перечитывает запись, отбрасывая локальные изменения. Без изменений полей save
всё равно выполняет UPDATE и увеличивает версию.

У users триггер увеличивает версию и при изменениях login/email/password_hash
через QueryBuilder. При добавлении других таблиц такая политика задаётся их схемой.
`attributes()` возвращает только записываемые колонки, без id и version.
`readAttributes()` заполняет поля; общие id/version читает Model.
`snapshotAttributes()` включает дополнительные поля только для чтения, необходимые
для восстановления модели при откате. Модель с такими полями переопределяет этот
метод, как User с датами. Во время обычной выборки копия строки в модели не хранится.

## Транзакции

```java
database.transaction(tx -> {
    User user = User.on(database).where("id", userId).firstOrFail();
    user.setEmail(newEmail);
    user.save();
    return user.getId();
});
```

Запросы и модели основного Database в текущем потоке присоединяются к его активной
транзакции, включая созданные до неё. После завершения они снова работают вне
транзакции. Смешивание разных объектов Database и вложенный transaction внутри
одной транзакции отклоняются.

`User.on(tx)` и `new User(tx)` сохранены для явного использования сессии. Такие
объекты нельзя использовать для новых запросов после выхода из функции. Модели,
созданные через основной объект, можно использовать после commit. Ни модели,
ни транзакционные соединения нельзя передавать параллельно работающим потокам.

При откате save/delete восстанавливают поля модели до соответствующего вызова,
включая id/version и генерируемые даты User. Если save вызван несколько раз,
восстановление выполняется в обратном порядке. Произвольные присваивания после
последнего save и внешние эффекты вроде файлов не являются частью транзакции.
Ошибка составной операции (save/delete/insertAll) помечает транзакцию для отката,
даже если вызывающий код поймал исключение. Ошибки отдельных низкоуровневых SQL
нужно пробрасывать для отката всего сценария.

Контекст ограничен текущим потоком. DatabaseTasks отклоняет постановку задачи
из активной транзакции: нужно поставить в очередь весь сценарий с transaction.
Произвольный самостоятельно созданный поток также не наследует транзакцию.
Вложенные транзакции, savepoint и распределённые транзакции не реализованы.

## Ограниченные выборки

```java
List<User> page = User.on(database).orderBy("login").page(1, 50).get();
List<User> next = User.on(database).afterId(lastId).limit(50).get();
long total = User.on(database).where("email", email).count();
boolean found = User.on(database).where("email", email).exists();

User.on(database).chunkById(100, users -> {
    // Обработка одной порции; результат JDBC уже закрыт.
});
```

`get()` без limit читает не больше defaultLimit + 1 строк. Если совпадений больше
лимита, он выбрасывает ResultLimitException. Это относится и к `User.on(database).get()`: данные
не обрезаются молча. Явный limit возвращает до указанного числа строк. Максимальный
размер страницы ограничен maxLimit. В памяти создаётся сразу список моделей,
без дополнительного полного списка карт строк.

`page()` нумеруется с 1, использует OFFSET и сортировку по id по умолчанию.
`orderBy(column, descending)` добавляет id для одинаковых значений колонки.
Эти методы рассчитаны на таблицы с уникальным id. `first()` без orderBy может
вернуть любое совпадение — для конкретной записи используйте уникальное условие.
Для глубоких страниц и обхода таблицы предпочтителен afterId/chunkById.
Курсор требует возрастающего целочисленного id. chunkById нельзя сочетать с
проекцией, явным limit или смещением. Обработчик не должен изменять id или
накапливать все порции в общем списке.

Порции не гарантируют снимок таблицы при конкурентных вставках/удалениях.
Для согласованного снимка нужна транзакция с подходящим режимом изоляции;
длительная транзакция может задерживать других клиентов.
`count()` и `exists()` учитывают WHERE, но игнорируют сортировку и страницу.

Проекции доступны только на уровне строк:

```java
var names = database.table("users").select("id", "login").limit(50).get();
```

ModelQuery всегда читает полную модель. Частично прочитанная строка не становится
моделью, у которой save мог бы записать отсутствующие поля как null.
Условия объединяются через AND; where(column, null) создаёт IS NULL.

## Пакетная запись

```java
database.table("users").insertAll(rows);
```

Один PreparedStatement и одна транзакция на пакет. Все карты должны иметь
одинаковые колонки, их порядок внутри карт может различаться. Размер от 1 до
maxBatch. При ошибке любой строки откатывается весь пакет. Метод не возвращает
ключи и не создаёт модели. Большие импорты вызывают его по ограниченным порциям;
каждая порция отдельно фиксируется, если нет внешней транзакции.

UPDATE/DELETE требуют WHERE или явного allRows(). Пагинация, проекция и сортировка
в запросах записи отклоняются: ограничения SELECT не будут молча проигнорированы.
Имена проверяются отдельно от параметров; произвольные SQL-выражения не принимаются.

## Нагрузка, фоновые операции и отмена

Настройки в config/database.properties:

| Настройка | По умолчанию | Назначение |
| --- | ---: | --- |
| max_connections | 4 | Одновременные операции с соединениями |
| max_waiting | 32 | Ожидающие операции |
| acquire_timeout_ms | 2000 | Ожидание свободного места |
| busy_timeout_ms | 5000 | Ожидание блокировки SQLite |
| query_timeout_ms | 5000 | Выполнение одного SQL-запроса |
| default_limit | 100 | Защита выборки без limit |
| max_limit | 1000 | Максимальный размер страницы |
| max_batch | 500 | Максимальный размер пакета |

Переполнение очереди или ожидание места дольше acquire_timeout_ms вызывает
DatabaseBusyException. Транзакция занимает одно место до commit/rollback.
Блокировки не обходятся бесконечными повторами.

SQLite-диалект ограничивает ожидание блокировки и устанавливает ProgressHandler
для прерывания вычислений по времени или сигналу отмены. Сам setQueryTimeout
SQLite JDBC ограничивает ожидание блокировки и не заменяет такой обработчик.
Отмена во время блокировки может ждать её тайм-аута. Это ограничения отдельного
SQL, а не жёсткий дедлайн всей транзакции, пользовательского Java-кода или ввода-вывода ОС.

```java
// Один исполнитель на срок работы приложения; close при завершении.
DatabaseTasks tasks = new DatabaseTasks(database);
Future<Long> result = tasks.submit(() -> database.transaction(tx -> {
    User user = User.on(database).where("email", email).firstOrFail();
    return user.getId();
}));
// result.cancel(true) запрашивает отмену SQL и прерывает ожидание.
```

DatabaseTasks ограничивает очередь ещё до запуска задач, не создаёт поток на
каждый запрос. При переполнении выбрасывает RejectedExecutionException. close
запрашивает отмену, но не обещает мгновенного завершения произвольного Java-кода.
Не вызывать Future.get() в JavaFX-потоке. Изменения UI выполняются в JavaFX-потоке;
бизнес-логика контроллеров в рамках этой работы не добавлялась.

Для собственного исполнителя можно использовать
`database.withCancellation(token, () -> operation())`; `token.cancel()` безопасен
из другого потока. Контекст отмены также не переносится автоматически.

## Пул и другая СУБД

`DatabaseConfigurator.configure(DataSource, SqlDialect, DatabaseOptions)` принимает
внешний пул. Приложение создаёт и закрывает его; сам коннектор получает и закрывает
заёмные соединения. После commit/rollback autoCommit восстанавливается.
DataSource должен выдавать свободное соединение с autoCommit=true. Пул обязан
сбрасывать прочие настройки и отбрасывать неисправные физические соединения.
Ожидание выдачи/создания соединения ограничивается настройками самого пула/драйвера;
acquire_timeout_ms ограничивает только очередь ядра.

Собственный пул в ядре не реализован. Текущий SQLiteDataSource открывает соединения
по необходимости. Для сетевой СУБД нужны её драйвер, конфиг, диалект, преобразование
типов (в частности дат User), схема/миграции и проверки generated keys, транзакций,
пакетов и отмены. Только SQLite проверена интеграционно.

Ограничения применяются к одному объекту DatabaseConnector. При нескольких
экземплярах приложения общий бюджет соединений согласуется с лимитом БД.
Не создавать отдельный коннектор на каждый запрос.

SQLite остаётся локальным хранилищем с одним писателем. Увеличение количества
потоков не делает запись линейно масштабируемой. Файл не переносится на сетевой
диск для имитации серверной БД. Для нескольких машин с общими данными понадобится
клиент-серверная СУБД. WAL можно включать отдельно после выбора режима эксплуатации;
ядро не меняет режим журнала существующей базы автоматически.

## Миграции и проверки

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/migrate-database.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-database.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-load.ps1
```

Миграция 001 добавляет users.version и обновляет триггер. До изменений создаётся
согласованная резервная копия app.db.backup-*. Приложение следует остановить на
время миграции. Повторный запуск обнаруживает колонку version. Новая база создаётся
из database/schema.sql скриптом `scripts/init-database.ps1`; существующий файл он
не перезаписывает. Запуск приложения сам схему не изменяет.

Тесты работают только с временными базами. Проверяются исходный CRUD, конкуренция,
версии, составные транзакции, отмена, очереди, пагинация, пакеты, миграция и возврат
соединения в пул. LoadProbe запускает два отдельных JVM-процесса, проверяет конфликт
версий и измеряет локальную смешанную нагрузку на 1/2/4/8 потоках.

`database.statistics()` возвращает число SQL-операций, ошибок и суммарное время
с ожиданием соединения. Снимок приблизительный при конкурентном обновлении.
Параметры и SQL не записываются. p95/p99 измеряются нагрузочной проверкой, а не
вычисляются из среднего времени. Результаты: [performance.md](performance.md).
